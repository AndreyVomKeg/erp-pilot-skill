# Спецификация — 2026-10-26-lager-filter

Каждое требование `R-n` получает решение `S-n`. `pilot.py check` ищет заголовок вида `### S-n — R-n: …`;
раздел без `S-n` и `R-n` в заголовке не считается спекой.

## Контекст и ограничения репозитория

- Правила: PR-only, squash-merge; миграции применяет администратор после слияния; UI-тексты DE и RU — см. `state.run.constraints`.
- Затрагиваемые модули: список заказов (`orders/OrdersList`), профиль сотрудника, политики доступа к складам.

## Решения

### S-1 — R-1: фильтр по складу в списке заказов

- **Данные:** новых таблиц нет; `orders.warehouse_id` уже есть. Параметр запроса `?lager=<id>`.
- **Права:** список заказов уже ограничен политиками доступа; фильтр их не расширяет.
- **UI:** выпадающий список складов в панели фильтров списка заказов, компонент выбора по стандарту репозитория; тексты DE/RU.
- **Крайние случаи:** неизвестный `lager` в URL → фильтр сброшен, подсказка; склад удалён → как неизвестный.
- **Не делаем:** мультивыбор складов.

### S-2 — R-2: видимость фильтра по праву lager:read

- **Данные:** нет.
- **Права:** проверка права `lager:read` на сервере (список складов отдаётся только с этим правом) и в UI (контрол скрыт без права).
- **UI:** без права — панель фильтров как сейчас; параметр `lager` в URL игнорируется.
- **Крайние случаи:** право отозвано в открытой сессии → следующий запрос списка складов возвращает пусто, контрол исчезает.
- **Не делаем:** отдельное право на фильтр.

### S-3 — R-3: склад по умолчанию из профиля

- **Данные:** поле `profiles.default_warehouse_id` (nullable) — миграция `…_default_warehouse.sql`, с явными правами на объект.
- **Права:** сотрудник меняет только своё поле; администратор — любое.
- **UI:** поле «Склад по умолчанию» в настройках профиля; при открытии списка без `?lager` подставляется это значение.
- **Крайние случаи:** в профиле пусто → все склады; склад из профиля недоступен по правам → все склады.
- **Не делаем:** автоопределение склада по геолокации.
