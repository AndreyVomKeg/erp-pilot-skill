# Этапы ERP Pilot: вход, выход, глубина

Читай раздел нужного этапа перед его началом. Статусы этапа в `state.json`: `ahead` → `active` → `done` | `skipped`.
Переход — только командой `pilot.py phase <id> start|done|skip`, чтобы таймер и журнал были честными.

## Сводная таблица

| # | Этап (`id`) | Вход | Выход (обязательный артефакт) | Ворота semi-automatic |
|---|---|---|---|---|
| 1 | Preflight (`preflight`) | бриф, доступ к репозиторию | ветка `pilot/<run-id>`, `state.json`, опубликованный дашборд | нет |
| 2 | Requirements (`requirements`) | бриф | `requirements.md`, все `R-n` в state со статусом `open` и `source` | **да** — список `R-n` подтверждён |
| 3 | Briefing (`briefing`) | список `R-n` | ответы записаны в `note` требований; неясных `R-n` нет | нет (вопросы сами по себе остановка) |
| 4 | Spec (`spec`) | `R-n` без вопросов | `spec.md`, у каждого `R-n` есть `spec: S-n`, статус `specified` | нет |
| 5 | Plan (`plan`) | `spec.md` | `plan.md`, тикеты `T-n` с `requirements`, у `R-n` статус `planned` | **да** — перед публикацией Issues |
| 6 | Development (`development`) | согласованный план | коммиты/PR, тикеты `done`, `R-n` → `implemented` | нет |
| 7 | Code review (`code_review`) | PR | отчёт ревью по двум осям; замечания → `T-n` | нет |
| 8 | Acceptance (`acceptance`) | ревью закрыто | `acceptance.md`, `pilot.py check` = 0 пропусков, `R-n` → `verified|dropped` | **да** — подпись пользователя |

## Глубина

| Что | `light` | `normal` | `deep` |
|---|---|---|---|
| Briefing | только блокирующие вопросы | вопросы по каждому неясному `R-n` | полный опрос (формат trid-grill), GLOSSARY/ADR |
| Spec | таблица `R-n → решение` | `spec.md` целиком | + схема данных, RLS-матрица, крайние случаи, миграции отдельно |
| Plan | 1–3 тикета, без Issues | тикеты с зависимостями, Issues после ворот | + оценка риска, порядок выката, откат |
| Development | один PR | один PR, коммиты по `T-n` | PR на тикет, скриншоты UI до/после |
| Code review | ось «стандарты» | обе оси | обе оси + регрессионный тест на каждое исправление |
| Acceptance | чек по списку `R-n` | + шаги на превью, скриншоты | + проверка на проде после слияния, запись в журнал |

## Детали по этапам

### 1. Preflight
- Узнай: репозиторий, ветка-основа (`main`), режим, глубина, язык дашборда по умолчанию (`ru`).
- Проверь правила репозитория (README/CONTRIBUTING/docs): PR-only, ограничения миграций, UI-стандарт, лимит preview-веток. Запиши их в `state.run.constraints`.
- Текст карточки этапа: «Настраиваю репозиторий и дашборд» / «Setting up the repo and the dashboard».

### 2. Requirements
- Атомарность: одно требование — одна проверяемая фраза. Склейки «и/или» режь.
- У каждого `R-n`: `text`, `source` (цитата или раздел брифа), `kind` (`functional` | `data` | `ui` | `security` | `ops`), `status: open`.
- Всё, чего в брифе нет, но без чего не сделать — `kind: proposed`; на воротах пользователь принимает или удаляет.
- Выход этапа: пользователь ответил «да» на список (semi-automatic/manual). В `automatic` — продолжай, но помечай в отчёте.

### 3. Briefing
- Формат вопроса: `R-3: <вопрос>` + варианты, если они есть. Не больше 7 вопросов за раз.
- Ответ пиши в `pilot.py req note R-3 "<ответ>"`. Если ответ меняет требование — правь `text` и добавь запись в журнал.
- Противоречия между `R-n` решай здесь, не в Spec.

### 4. Spec
- Для каждого `R-n` — раздел `S-n` в `spec.md`: данные (таблицы/поля), права (RLS, роли), UI (экран, список/диалог по стандарту репозитория), крайние случаи, что не делаем.
- `pilot.py req set R-n --spec S-n --status specified`.
- Блокер: `pilot.py check --phase spec` показывает `R-n` без спеки.

### 5. Plan
- Тикет вертикальный: миграция + API/функция + UI + тест в одном `T-n`, если глубина не `deep`.
- Поля: `title`, `requirements: [R-n]`, `depends_on: [T-m]`, `acceptance: [...]`, `status: todo`.
- Issues публикуй после ворот; URL — в `pilot.py ticket set T-n --url`.

### 6. Development
- Перед первым коммитом: `pilot.py ticket set T-1 --status in_progress`.
- Коммит: `T-1: <что сделано>`. PR-описание — таблица `T-n → R-n`.
- Не расширяй объём: новое пожелание пользователя → новое `R-n` (`proposed`) и решение на следующих воротах.

### 7. Code review
Чек-лист, если `trid-code-review` недоступен:
- **Стандарты:** правила репозитория соблюдены; миграции идемпотентны и не в запрещённых ветках; RLS/права на новые таблицы и функции; UI использует стандартные компоненты списков/диалогов; нет секретов в коде; тексты UI на языке интерфейса.
- **Спека:** каждое `S-n` реализовано; крайние случаи покрыты; ничего лишнего «по дороге».
- Каждое замечание → `T-n` (новый или `status: review` у существующего). Ревью закрыто, когда замечаний `open` нет.

### 8. Acceptance
- `pilot.py check` — 0 пропусков: все `R-n` в `verified` или `dropped` (с `reason`), все `T-n` в `done` или `dropped`.
- `acceptance.md`: для каждого `R-n` шаг проверки, где проверено (превью/прод), результат, скриншот.
- Подпись пользователя — текстом в чате; затем `pilot.py phase acceptance done`, финальный `render`, публикация, отчёт.
