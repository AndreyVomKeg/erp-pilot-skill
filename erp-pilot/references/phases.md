# Этапы ERP Pilot: вход, выход, глубина

Читай раздел нужного этапа перед его началом. Статусы этапа в `state.json`: `ahead` → `active` → `done` | `skipped`.
Переход — только командой `pilot.py phase <id> start|done|skip`. `done` сам запускает проверку трассировки
для этапа (колонка «Проверка `done`») и отказывает при пропусках; `skip` возможен только для активного или
следующего этапа и невозможен для `requirements` и `acceptance`.

## Сводная таблица

| # | Этап (`id`) | Вход | Выход (обязательный артефакт) | Проверка `done` | Ворота semi-automatic |
|---|---|---|---|---|---|
| 1 | Preflight (`preflight`) | бриф, доступ к репозиторию | ветка `pilot/<run-id>`, `state.json`, constraints, helpers, опубликованный дашборд | — | нет |
| 2 | Requirements (`requirements`) | бриф | все `R-n` в state со `source`; строка `\| R-n \|` в `requirements.md` | ≥1 требование, у каждого источник и строка в таблице | **да** — список `R-n` подтверждён |
| 3 | Briefing (`briefing`) | список `R-n` | ответы в `note` требований; неясных `R-n` нет | как у Requirements | нет (вопросы сами по себе остановка) |
| 4 | Spec (`spec`) | `R-n` без вопросов | у каждого живого `R-n` есть `spec: S-n` и заголовок `### S-n — R-n` в `spec.md` | + спека и заголовок у каждого `R-n` | нет |
| 5 | Plan (`plan`) | `spec.md` | `plan.md`, тикеты `T-n` с `requirements`, `R-n` → `planned` | + живой тикет у каждого `R-n`, у каждого `T-n` есть `R-n` | **да** — перед публикацией в трекер |
| 6 | Development (`development`) | согласованный план | коммиты/PR, тикеты `review` или `done` | + нет тикетов `todo`/`in_progress` | нет |
| 7 | Code review (`code_review`) | PR | отчёт ревью по двум осям; замечания → `T-n` | + все тикеты `done`/`dropped` | нет |
| 8 | Acceptance (`acceptance`) | ревью закрыто | `acceptance.md`, `R-n` → `verified`/`dropped` | + каждое `R-n` `verified`/`dropped` с причиной и строкой в `acceptance.md` | **да** — подпись пользователя |

## Глубина

| Что | `light` | `normal` | `deep` |
|---|---|---|---|
| Briefing | только блокирующие вопросы | вопросы по каждому неясному `R-n` | полный опрос (навык роли `interview`), глоссарий/ADR проекта |
| Spec | таблица `R-n → решение` + минимальные разделы `S-n` | `spec.md` целиком | + схема данных, матрица прав, крайние случаи, миграции отдельно |
| Plan | 1–3 тикета, без публикации в трекер | тикеты с зависимостями, публикация после ворот | + оценка риска, порядок выката, откат |
| Development | один PR | один PR, коммиты по `T-n` | PR на тикет, скриншоты UI до/после |
| Code review | ось «стандарты» | обе оси | обе оси + регрессионный тест на каждое исправление |
| Acceptance | чек по списку `R-n` | + шаги на превью, скриншоты | + проверка на проде после слияния, запись в журнал |

## Детали по этапам

### 1. Preflight — окно запуска

Покажи одно окно выбора (до трёх вопросов), если ответы не следуют из запроса пользователя. Варианты — ровно эти:

**Режим** — «Где останавливаться и спрашивать вас?»
- `Ручной` — пауза после каждого из восьми этапов; максимум контроля.
- `Полуавтомат` (по умолчанию) — остановки только на воротах: после списка требований, на вопросах по брифу, после плана, перед подписью приёмки.
- `Автомат` — только блокеры и финальный отчёт; код пишется без промежуточных согласований.
  Предупреди в тексте варианта: этот режим отключает ворота после Requirements и Plan — остаются только подпись
  Acceptance и запрет сливать PR без слова пользователя.

**Глубина** — «Насколько подробные артефакты и проверки нужны?»
- `Лёгкая` — только блокирующие вопросы, 1–3 тикета, один PR, ревью по стандартам.
- `Обычная` (по умолчанию) — вопросы по каждому неясному требованию, полная спека, тикеты с зависимостями, ревью по двум осям.
- `Глубокая` — полный опрос с глоссарием/ADR, схема данных и матрица прав, PR на тикет, регрессионные тесты, проверка на проде.

**Служебные файлы** (только если защита основной ветки не позволяет решить самому) — «Что делать с папкой `.pilot/` при слиянии?»
- `Оставить как журнал` — артефакты прогона попадают в основную ветку вместе с кодом.
- `Удалить перед слиянием` — последний коммит PR убирает `.pilot/`; дашборд остаётся опубликованным сайтом.

Выбранное запиши: `pilot.py init --mode … --depth …` и `pilot.py set --constraint ".pilot/: <решение>"`.
Если пользователь назвал режим словами («вручную», «сам», «поглубже»), сопоставь и окно не показывай.

### 1. Preflight — чек-лист

Выясни и запиши `pilot.py set --constraint "<правило>"` каждое из найденного (источник: README, CONTRIBUTING, `docs/`,
настройки защиты ветки, CI-workflows):

- основная ветка и защита: PR-only, обязательные проверки, тип слияния, удаление веток;
- какие проверки гоняет CI (типы, unit, e2e, линт миграций) и что из этого должно быть зелёным до ревью;
- правила миграций и серверных функций: кто и когда применяет, идемпотентность, явные права на новые объекты;
- UI-стандарт: дизайн-система/гайд, компоненты списков и диалогов, языки интерфейса и способ локализации;
- деплой и превью: откуда собирается прод, есть ли превью на PR, лимит превью-веток;
- служебные файлы: допустим ли `.pilot/` в основной ветке (см. SKILL.md, «Артефакты прогона»);
- план развития репозитория (`docs/ENTWICKLUNGSPLAN.md`, `ROADMAP.md`, `docs/PLAN*.md`): прочитай его целиком, найди
  этап и шаг для брифа, проверь, что предшествующие шаги закрыты или бриф явно их не требует; запиши
  `--constraint "План: этап N, шаг N.m (<файл>); вне шага → proposed и Parkplatz"`. Открытые решения владельца из
  плана, от которых зависит шаг, — первые вопросы Briefing;
- вспомогательные навыки из каталога по ролям `interview`, `tickets`, `review`, `diagnose`, `design` →
  `pilot.py set --helper role=имя`. Записывай только реально установленные навыки.

Карточка этапа: «Настраиваю репозиторий и дашборд» / «Setting up the repo and the dashboard».

### 2. Requirements
- Атомарность: одно требование — одна проверяемая фраза. Склейки «и/или» режь.
- У каждого `R-n`: `text`, `source` (цитата или раздел брифа), `kind` (`functional` | `data` | `ui` | `security` | `ops`), `status: open`.
- Всё, чего в брифе нет, но без чего не сделать — `kind: proposed`; на воротах пользователь принимает или удаляет.
- Заполни таблицу `requirements.md`: `check` ищет строку `| R-n |` для каждого требования.
- Ворота: полный список `R-n` по областям — сообщением в чат (и он уже на дашборде); окно — один вопрос
  «Подтверждаете список требований?» с вариантами `Подтверждаю` / `Нужны правки`, в теле только счётчик
  (`N требований, из них M proposed`). Не вставляй список в тело окна и не смешивай ворота с вопросами Briefing.
- Выход этапа: пользователь ответил «да» (окном или текстом). В `automatic` — продолжай, но помечай в отчёте.

### 3. Briefing
- Формат вопроса: `R-3: <вопрос>` + варианты. Сначала вопросы текстом в чат, затем окно: не больше 3 вопросов
  в одном окне, у каждого варианты ответа; длинные пояснения — в чат, не в тело окна. Ответ текстом принимается.
- Ответ пиши в `pilot.py req note R-3 "<ответ>"`. Если ответ меняет требование — правь `--text` и добавь запись в журнал.
- Противоречия между `R-n` решай здесь, не в Spec.

### 4. Spec
- Для каждого `R-n` — раздел `### S-n — R-n: <имя>` в `spec.md`: данные (таблицы/поля), права (роли, политики
  доступа, серверные функции), UI (экран, список/диалог по стандарту репозитория), крайние случаи, что не делаем.
- `pilot.py req set R-n --spec S-n` (статус станет `specified`).
- Блокер: `pilot.py check --phase spec` показывает `R-n` без спеки или без заголовка.

### 5. Plan
- Тикет вертикальный: миграция + API/функция + UI + тест в одном `T-n`, если глубина не `deep`.
- Поля: `title`, `requirements: [R-n]`, `depends_on: [T-m]`, `acceptance: [...]`, `status: todo`.
- В трекер публикуй после ворот; URL — `pilot.py ticket set T-n --url`.

### 6. Development
- Перед первым коммитом: `pilot.py ticket set T-1 --status in_progress`.
- Коммит: `T-1: <что сделано>`. PR-описание — таблица `T-n → R-n`.
- Тикет, отданный на ревью, — `--status review`; `done` ставь после закрытия замечаний.
- Не расширяй объём: новое пожелание пользователя → новое `R-n` (`proposed`) и решение на следующих воротах.

### 7. Code review
Чек-лист, если навык роли `review` не записан:
- **Стандарты:** правила репозитория из `constraints` соблюдены; миграции идемпотентны и не в запрещённых ветках;
  права на новые таблицы и функции заданы явно; UI использует стандартные компоненты списков/диалогов; нет секретов
  в коде; тексты UI на всех языках интерфейса проекта.
- **Спека:** каждое `S-n` реализовано; крайние случаи покрыты; ничего лишнего «по дороге».
- Каждое замечание → `T-n` (новый или `status: review` у существующего). Ревью закрыто, когда все тикеты `done`/`dropped`.

### 8. Acceptance
- `acceptance.md`: для каждого `R-n` строка `| R-n | шаг | где | результат | скриншот |`.
- `pilot.py req set R-n --status verified` — только после `done` всех его тикетов; `dropped` — с `--reason`.
- Подпись пользователя — текстом в чате; затем `pilot.py phase acceptance done` (сам проверит трассировку и поставит
  `finished_at`), финальный `render`, публикация, отчёт.
