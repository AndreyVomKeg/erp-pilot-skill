# ERP Pilot — от брифа до приёмки

Один прогон (run) = один бриф пользователя = одна ветка и один набор артефактов в целевом репозитории
под `.pilot/<run-id>/`. Источник истины — `state.json`; дашборд только отображает его.
Главное правило: **ни одно требование из брифа не теряется** — каждое `R-n` заканчивает прогон статусом
`verified` или `dropped` с причиной, подтверждённой пользователем. Язык общения и артефактов — русский;
термины интерфейса — как на экране целевого продукта.

`scripts/pilot.py` защищает процесс сам: этапы открываются по порядку, `phase <id> done` закрывает этап только без
пропусков трассировки (включая строки в `requirements.md`, `spec.md`, `acceptance.md`), `requirements` и
`acceptance` нельзя пропустить, статусы `R-n` идут только вперёд. Отказ скрипта — исправь пропуск.
`--force` и `--reopen` — только по явному слову пользователя; они журналируются и попадают в отчёт.

## Режимы и глубина

Если пользователь не назвал режим и глубину в запросе, в Preflight покажи **окно выбора** с вариантами и
пояснениями (тексты — `references/phases.md`, «Окно запуска»); не проси вспоминать названия режимов.

| Параметр | Значения | Что меняет |
|---|---|---|
| Режим | `manual` · `semi-automatic` (по умолчанию) · `automatic` | manual — пауза после каждого этапа; semi-automatic — на воротах (после Requirements, после Plan, перед подписью Acceptance) и при любом вопросе; automatic — только блокеры и финал |
| Глубина | `light` · `normal` (по умолчанию) · `deep` | Объём артефактов и проверок — `references/phases.md`, таблица «Глубина» |

## Ворота и вопросы: как показывать

Сначала полный материал (список `R-n`, план, вопросы) — обычным сообщением в чате и на дашборде. Потом окно выбора:
в теле — одна-две строки («21 требование, 3 из них proposed»), не список; один вопрос на ворота с вариантами
`Подтверждаю` / `Нужны правки`; вопросы Briefing — отдельным окном, до 3 за раз, каждый с вариантами.
Ответ текстом в чате («да», «1 — да, 2 — только чтение», «R-5 убрать») принимай наравне с окном.
Если пользователь пишет, что окно не отправляется или зависло, — повтори вопросы нумерованным текстом и жди ответа
в чате, окно больше не показывай для этих ворот.

## Шаги

1. **Preflight.** Репозиторий, `run-id` (`YYYY-MM-DD-краткое-имя`); режим, глубина и судьба `.pilot/` — через окно
   запуска (`references/phases.md`), если не заданы. Пройди чек-лист Preflight в
   `references/phases.md`: правила репозитория → `pilot.py set --constraint`, навыки проекта по ролям →
   `pilot.py set --helper role=имя`. Ветка `pilot/<run-id>` от основной, `pilot.py init`, `render`, публикация
   дашборда как сайта, адрес → `pilot.py set --dashboard-url`. Этап закрыт, когда пользователь видит дашборд.
2. **Requirements.** Бриф → атомарные `R-1…R-n` с источником через `pilot.py req add`; таблица в `requirements.md`.
   Ворота semi-automatic: список — сообщением в чат, затем короткое окно `Подтверждаю` / `Нужны правки`.
3. **Briefing.** Вопросы только по неясным `R-n`, с номером. Ответы → `pilot.py req note`. Формат — навык роли
   `interview`, если записан.
4. **Spec.** В `spec.md` на каждое `R-n` раздел `### S-n — R-n: …` (данные, права, UI, крайние случаи);
   `pilot.py req set R-n --spec S-n`.
5. **Plan.** Вертикальные `T-n` с зависимостями и критериями приёмки, каждый на `R-n` (`pilot.py ticket add --req`).
   Публикация в трекер репозитория — после ворот. Формат карточки — навык роли `tickets`, если записан.
6. **Development.** `pilot.py ticket set T-n --status in_progress|review|done`, коммиты с `T-n` в теме, один PR на
   прогон (на тикет при `deep`). Правила репозитория (миграции, PR-only, UI-стандарт, языки UI) сильнее навыка.
7. **Code review.** Оси «стандарты» и «соответствие спеке». Навык роли `review`, иначе чек-лист в
   `references/phases.md`. Замечания → новые или вновь открытые `T-n`, не правки мимо тикетов.
8. **Acceptance.** Таблица `acceptance.md` (строка `| R-n |` с шагом, местом, результатом, скриншотом на каждое
   требование). Ворота: подпись пользователя → `pilot.py phase acceptance done` → финальный рендер, публикация, отчёт.

Рендер — после каждой команды, изменившей состояние; публикация сайта — на воротах, при закрытии этапа и в финале
(тот же сайт). Подробности — `references/dashboard.md`.

## Артефакты прогона (в целевом репозитории)

```
.pilot/<run-id>/
  state.json           # истина: run, phases, requirements, tickets, log
  requirements.md  spec.md  plan.md  acceptance.md   # из templates/, их читает pilot.py check
  dashboard/index.html # результат pilot.py render (не редактировать руками)
```

Если правила репозитория не допускают служебные файлы в основной ветке, согласуй в Preflight: удалить `.pilot/`
перед слиянием или оставить как журнал. Решение → `--constraint`.

## Что читать и когда

- `references/phases.md` — чек-лист Preflight, вход/выход этапов, глубина, чек-лист ревью. В начале каждого этапа.
- `references/dashboard.md` — схема `state.json`, тексты карточек RU/EN, публикация. В Preflight и при ошибке рендера.
- `scripts/README.md` — команды и защиты `pilot.py`. `scripts/pilot.py` — выполняй, не пересказывай.
- `templates/*.md` — копирует `pilot.py init`; заполняй, структуру заголовков и таблиц не меняй.

## Границы

- Не трогай основную ветку напрямую и не сливай PR без слова пользователя.
- Не изобретай требования: всё, чего нет в брифе и ответах Briefing, — `kind: proposed` и вопрос.
- Не обещай триггеров из репозитория: дашборд обновляется шагами прогона, не событиями.
- Отчёт в конце по-русски: ссылки на PR и дашборд, таблица `R-n → статус`, `dropped` с причинами, все
  `--force`/`--reopen` из журнала.
