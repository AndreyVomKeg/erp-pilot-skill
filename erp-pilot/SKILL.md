# ERP Pilot — от брифа до приёмки

Один прогон (run) = один бриф пользователя = одна ветка и один набор артефактов в целевом репозитории
под `.pilot/<run-id>/`. Источник истины о ходе прогона — `state.json`; дашборд только отображает его.
Главное правило: **ни одно требование из брифа не теряется** — каждое `R-n` заканчивает прогон статусом
`verified` или `dropped` с причиной, подтверждённой пользователем. Язык общения и артефактов — русский;
термины интерфейса ERP — немецкие, как в UI.

## Режимы и глубина (спроси в Preflight, если не названы)

| Параметр | Значения | Что меняет |
|---|---|---|
| Режим | `manual` · `semi-automatic` (по умолчанию) · `automatic` | Где останавливаться: manual — после каждого этапа; semi-automatic — на воротах (после Requirements, после Plan, перед подписанием Acceptance) и при любом вопросе; automatic — только блокеры и финал |
| Глубина | `light` · `normal` (по умолчанию) · `deep` | Объём артефактов и проверок — см. `references/phases.md`, таблица «Глубина» |

## Шаги

1. **Preflight.** Определи целевой репозиторий, `run-id` (`YYYY-MM-DD-краткое-имя`), режим, глубину. Создай ветку
   `pilot/<run-id>` от `main`, выполни `python3 scripts/pilot.py init` (см. `scripts/README.md`), сделай рендер
   дашборда `pilot.py render` и опубликуй его как сайт; адрес запиши `pilot.py set --dashboard-url`. После каждого
   изменения состояния — `render` и повторная публикация того же сайта. Этап закрыт, когда пользователь видит дашборд.
2. **Requirements.** Разбери бриф на атомарные требования `R-1…R-n` с источником (цитата/раздел брифа) через
   `pilot.py req add`. Заполни `templates/requirements.md`. Ворота semi-automatic: покажи список, получи «да».
3. **Briefing.** Вопросы только по неясным `R-n` (связывай вопрос с номером). Ответы — в `state.json` через
   `pilot.py req note`. Если установлен skill `trid-grill` — используй его формат опроса и ведение GLOSSARY/ADR.
4. **Spec.** `templates/spec.md`: каждое `R-n` получает решение `S-n` (данные, RLS/права, UI, крайние случаи).
   `pilot.py req set R-n --spec S-n`. Требование без спеки — блокер этапа.
5. **Plan.** Вертикальные тикеты `T-n` с зависимостями и критериями приёмки, каждый ссылается на `R-n`
   (`pilot.py ticket add --req`). Публикация в GitHub Issues — только после согласования (ворота). При наличии
   `trid-tickets` — его формат карточки.
6. **Development.** По тикету: `pilot.py ticket set T-n --status in_progress|review|done`, коммиты с `T-n` в теме,
   один PR на прогон (или на тикет при `deep`). Правила целевого репозитория (миграции, PR-only, UI-стандарт) сильнее этого skill.
7. **Code review.** Две оси — стандарты и соответствие спеке. При наличии `trid-code-review` запусти его; иначе
   чек-лист в `references/phases.md`. Замечания → новые или вновь открытые `T-n`, не правки «мимо» тикетов.
8. **Acceptance.** `pilot.py check` должен пройти без пропусков (каждое `R-n` → `verified|dropped`). Заполни
   `templates/acceptance.md` с шагами проверки на превью/проде, приложи скриншоты. Ворота: подпись пользователя,
   затем `pilot.py phase acceptance done`, финальный рендер, отчёт.

## Артефакты прогона (в целевом репозитории)

```
.pilot/<run-id>/
  state.json           # истина: run, phases, requirements, tickets, log
  requirements.md  spec.md  plan.md  acceptance.md   # из templates/
  dashboard/index.html # результат pilot.py render (не редактировать руками)
```

## Что читать и когда

- `references/phases.md` — критерии входа/выхода каждого этапа, таблица глубины, чек-лист ревью. Читай в начале каждого этапа.
- `references/dashboard.md` — схема `state.json`, тексты карточки этапов RU/EN, как публиковать и обновлять дашборд. Читай в Preflight и при ошибке рендера.
- `scripts/README.md` — команды `pilot.py`. `scripts/pilot.py` — выполняй, не пересказывай.
- `templates/*.md` — копируй в `.pilot/<run-id>/` и заполняй; структуру заголовков не меняй (по ним `pilot.py check` ищет пропуски).

## Границы

- Не трогай `main` напрямую и не сливай PR без слова пользователя.
- Не изобретай требования: всё, чего нет в брифе и ответах Briefing, помечай `proposed` и спрашивай.
- Не обещай автоматических триггеров GitHub → Perplexity; дашборд обновляется при каждом шаге прогона, а не по событиям.
- Отчёт в конце: по-русски, со ссылками на PR, дашборд, таблицей `R-n → статус` и списком `dropped` с причинами.
